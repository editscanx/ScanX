# ScanX — خارطة طريق تطوير المشروع

**الحالة:** مسودة تنظيمية مقترحة للمراجعة، وليست اعتمادًا نهائيًا للنطاق أو خطة إصدار.
**الغرض:** تنظيم العمل على ScanX بمراحل واضحة ومهام قابلة للمتابعة، مع فصل ما قرره المستخدم عما لم يُحسم بعد.
**قاعدة أساسية:** لا تُعد أي فكرة أو مرحلة معتمدة لمجرد إدراجها هنا. لا يُحدد إصدار مستهدف قبل قرار صريح من المستخدم.

## طريقة إدارة العمل الحالية

- **التركيز الحالي هو جمع الأفكار ومناقشتها وتطويرها فقط.** لا نبدأ الآن التخطيط التنفيذي التفصيلي أو ترتيب الاعتماديات بين المهام والمراحل؛ يُؤجل ذلك إلى وقت لاحق عندما يطلب المستخدم الانتقال إليه.
- يمكن للمستخدم طرح الأفكار في أي وقت، حتى لو تعارضت مع أفكار سابقة أو بدت غير منطقية أو صعبة التنفيذ.
- نسجل الفكرة ونناقش هدفها وتفاصيلها وحالاتها المحتملة، ونوضح أي غموض أو مشكلة تظهر أثناء النقاش دون افتراض إجابة نيابة عن المستخدم.
- عند اكتشاف تعارض، نحدد الفكرة أو القرار السابق ذي الصلة ونشرح موضع التعارض والخيارات الممكنة. لا نغيّر أو نحذف قرارًا سابقًا بصمت.
- تبقى الفكرة في حالة مناسبة مثل: **واردة، قيد النقاش، تحتاج توضيحًا، مؤجلة، معتمدة، مرفوضة**. تسجيل الفكرة أو تطويرها لا يعني اعتمادها.
- يمكن لاحقًا اعتماد الفكرة أو رفضها أو تأجيلها أو تعديلها، مع توثيق قرار المستخدم عند حدوثه. ولا نفترض أن كل فكرة ستُنفذ.
- نفرّق في الوثائق بين: **ما ذكره المستخدم، وما اتُّفق عليه صراحة، والاقتراحات، والأسئلة المفتوحة، والملاحظات أو التعارضات المحتملة**.
- لا نبدأ البرمجة ولا نثبت الاعتماديات أو إصدارًا أو موعد إطلاق في هذه المرحلة. تُراجع خارطة التنفيذ وتُستكمل عندما يقرر المستخدم الانتقال من جمع الأفكار إلى التخطيط.

## المرحلة 0 — تنظيم المشروع وطريقة اتخاذ القرارات

**الهدف:** تأسيس طريقة عمل تمنع ضياع القرارات أو اختلاط الأفكار بالتزامات التنفيذ.

- [ ] 0.1 مراجعة بنية المستودع والوثائق الموجودة.
- [ ] 0.2 اعتماد طريقة موحدة لتسجيل القرارات والأسئلة المفتوحة والمهام.
- [ ] 0.3 إنشاء سجل للمخاطر والاعتماديات بين أجزاء المشروع.
- [ ] 0.4 تحديد آلية مراجعة واعتماد مخرجات كل مرحلة مع المستخدم.

**مخرج المرحلة:** خريطة وثائق واضحة وسجل مهام وقرارات قابل للتتبع.

## المرحلة 1 — الرؤية والنطاق والأولويات

**الهدف:** تحديد ما هو ScanX، ومن يخدم، وما الذي يدخل في النطاق الأولي دون افتراض إصدار.

- [ ] 1.1 مراجعة وثيقة الرؤية والهوية وتأكيد الهدف الأساسي.
- [ ] 1.2 حصر أقسام التطبيق وحدود كل قسم.
- [ ] 1.3 التمييز بين المتطلبات الضرورية والأفكار المستقبلية.
- [ ] 1.4 تحديد ما هو خارج النطاق صراحة.
- [ ] 1.5 توثيق المصطلحات الأساسية، مثل الرصيد الحالي وصافي الثروة والدخل والحركة الداخلية.

**مخرج المرحلة:** وثيقة رؤية ونطاق واضحة ومراجعة من المستخدم.

## المرحلة 2 — المتطلبات التفصيلية وسيناريوهات الاستخدام

**الهدف:** تحويل كل فكرة إلى سلوك مفهوم يمكن تصميمه واختباره.

- [ ] 2.1 تفصيل التسجيل المالي الابتدائي وتصحيح الأرصدة الحالية (IDEA-001).
- [ ] 2.2 تفصيل سجل المصاريف الشخصية وتعديلاته وحذفه والبحث فيه (IDEA-002).
- [ ] 2.3 تفصيل تسجيل بيانات الكابتن والشفتات والدخل التراكمي (IDEA-003).
- [ ] 2.4 تفصيل المستودع الثانوي والحذف والاستعادة والتراجع وإعادة الضبط (IDEA-004).
- [ ] 2.5 تحديد الحالات الاستثنائية لكل ميزة، وما يحدث عند نقص البيانات أو إدخال بيانات غير صحيحة.
- [ ] 2.6 كتابة معايير قبول قابلة للتحقق لكل متطلب.

**مخرج المرحلة:** متطلبات وسيناريوهات ومعايير قبول؛ لا تُعتبر الأفكار الأصلية معتمدة تلقائيًا.

## المرحلة 3 — قواعد البيانات المالية والحسابات

**الهدف:** تثبيت المعنى الدقيق لكل رقم وطريقة تحديثه قبل بناء الواجهات أو التحليلات.

- [ ] 3.1 توثيق معادلات الرصيد الحالي وصافي الثروة والدخل والمصروفات والديون.
- [ ] 3.2 تعريف التحويلات الداخلية ومنع احتسابها دخلًا أو مصروفًا مرة أخرى.
- [ ] 3.3 تعريف الفرق بين الرصيد الابتدائي وتصحيح الرصيد والحركة المالية الجديدة.
- [ ] 3.4 توثيق قواعد الدخل التراكمي لأوبر وحالات الشفت الواحد أو تعدد الشفتات والقراءات غير المكتملة.
- [ ] 3.5 التحقق من حدود اليوم والأسبوع في أرباح أوبر السعودية من مصدر مناسب قبل اعتماد التنفيذ.
- [ ] 3.6 تحديد كيفية تحديث التقارير عند تعديل أو حذف أو استعادة سجل.
- [ ] 3.7 إعداد أمثلة رقمية مرجعية لاختبار كل معادلة.

**مخرج المرحلة:** قاموس بيانات وقواعد حساب وأمثلة نتائج متوقعة معتمدة من المستخدم.

## المرحلة 4 — تجربة المستخدم وتصميم الشاشات

**الهدف:** تحديد كيف يتعامل المستخدم مع التطبيق قبل اختيار تفاصيل التنفيذ.

- [ ] 4.1 رسم خريطة التنقل بين الأقسام.
- [ ] 4.2 تصور الواجهة الرئيسية وأولوية الرصيد الحالي وصافي الثروة.
- [ ] 4.3 تصميم تدفقات إضافة البيانات وتعديلها وحذفها وتصحيحها.
- [ ] 4.4 تصميم البحث والفرز والتصفية والسجلات التاريخية.
- [ ] 4.5 تصميم تحذيرات الاستعادة والتراجع، مع إظهار البيانات المتأثرة وترك القرار للمستخدم.
- [ ] 4.6 مراجعة سهولة الاستخدام مع المستخدم قبل اعتماد التصاميم.

**مخرج المرحلة:** مخططات وتدفقات واجهات معتمدة قبل تنفيذها.

## المرحلة 5 — التصميم التقني والخصوصية والحماية

**الهدف:** اختيار طريقة تنفيذ تناسب المتطلبات بعد وضوحها، وليس قبل ذلك.

- [ ] 5.1 مقارنة خيارات التخزين المحلي والنسخ الاحتياطي والتصدير وفق احتياجات المشروع.
- [ ] 5.2 تحديد نموذج البيانات والعلاقات ومعرّفات السجلات.
- [ ] 5.3 تصميم فصل البيانات الأساسية عن المستودع الثانوي.
- [ ] 5.4 تحديد ما يسجل في المستودع وما يستثنى منه.
- [ ] 5.5 تصميم آلية آمنة للاستعادة والتراجع وإعادة ضبط المستودع، ومنع التكرار في الحسابات.
- [ ] 5.6 تحديد حماية البيانات والتصدير والاحتفاظ بالبيانات.
- [ ] 5.7 تقييم خيارات التحليل المحلي والخدمات الخارجية وتكلفتها وخصوصيتها.

**مخرج المرحلة:** قرار تقني مبرر وتصميم بيانات وحماية قابل للمراجعة.

## المرحلة 6 — خطة التنفيذ والبناء

**الهدف:** تحويل المتطلبات والتصاميم المعتمدة إلى مهام تطوير صغيرة قابلة للاختبار.

- [ ] 6.1 تقسيم التنفيذ إلى وحدات ومهام مرتبة حسب الاعتماديات.
- [ ] 6.2 تحديد معايير الإنجاز لكل مهمة.
- [ ] 6.3 بناء الهيكل الأساسي للتطبيق والتنقل.
- [ ] 6.4 تنفيذ وحدات البيانات والحسابات وفق ترتيب متفق عليه.
- [ ] 6.5 تنفيذ الواجهات وربطها بالبيانات.
- [ ] 6.6 تنفيذ المستودع الثانوي بعد اعتماد متطلباته وتصميمه.
- [ ] 6.7 توثيق كل تغيير ومراجعة أثره على بقية الوحدات.

**مخرج المرحلة:** نسخة تعمل وفق نطاق متفق عليه، دون افتراض إصدار مستهدف مسبقًا.

## المرحلة 7 — الاختبار وضمان الجودة

**الهدف:** التأكد من أن النتائج صحيحة وأن التعديلات لا تفسد بيانات أخرى.

- [ ] 7.1 اختبار المعادلات بأمثلة مرجعية.
- [ ] 7.2 اختبار التحويلات لمنع العد المزدوج.
- [ ] 7.3 اختبار تعديل السجلات وحذفها واستعادتها والتراجع عنها.
- [ ] 7.4 اختبار التحذيرات والأثر المتوقع قبل الاستعادة، بما في ذلك حالات عدم اليقين.
- [ ] 7.5 اختبار إعادة ضبط المستودع والتأكد من عدم تغيير البيانات الأساسية.
- [ ] 7.6 اختبار البحث والفرز والتصفية والتصدير.
- [ ] 7.7 توثيق العيوب وقرار إصلاحها والتحقق من الإصلاحات.

**مخرج المرحلة:** نتائج اختبار واضحة وقائمة عيوب معروفة قبل أي إطلاق.

## المرحلة 8 — مراجعة الإطلاق والتشغيل والتحسين

**الهدف:** اتخاذ قرار إطلاق مبني على نتائج الاختبار والجاهزية.

- [ ] 8.1 مراجعة اكتمال المتطلبات ومعايير القبول.
- [ ] 8.2 مراجعة النسخ الاحتياطي والتصدير واستعادة البيانات.
- [ ] 8.3 مراجعة الخصوصية والأداء وسهولة الاستخدام.
- [ ] 8.4 حصر القيود المعروفة وإبلاغ المستخدم بها.
- [ ] 8.5 اتخاذ قرار الإطلاق وتحديد الإصدار فقط بموافقة صريحة.
- [ ] 8.6 تسجيل الملاحظات وترتيب التحسينات التالية.

**مخرج المرحلة:** قرار إطلاق أو قائمة نواقص واضحة تمنع الإطلاق.

## سجل المخاطر والاعتماديات الأولي

- **صحة الحسابات:** خطأ في تعريف الرصيد أو الدخل قد ينتشر إلى جميع التقارير.
- **تكرار الاحتساب:** التحويلات أو الاستعادة قد تسبب احتساب حركة أكثر من مرة إذا لم تُصمم قواعدها بعناية.
- **فقدان التاريخ:** إعادة بناء المستودع الثانوي قد تفقد تفاصيل قديمة لا يمكن استنتاجها من البيانات الحالية.
- **حدود احتساب أوبر:** يجب التحقق من الحدود الفعلية قبل تثبيت قواعد اليوم والأسبوع.
- **نطاق التسجيل:** يجب تعريف الأحداث التي تُسجل والاستثناءات صراحة، بدل استخدام عبارة «كل شيء» دون حدود.
- **الخصوصية والتكلفة:** التصدير والخدمات الخارجية يجب أن يتوافقا مع رغبة المستخدم في التحكم ببياناته وتقليل التكلفة.

## القرارات المفتوحة ذات الأولوية

1. طريقة تصحيح الرصيد الحالي بعد التسجيل الأول.
2. طريقة تسجيل المسافة: لكل شفت أم يوميًا أم كلاهما.
3. الحالات الاستثنائية للدخل التراكمي في أوبر.
4. نطاق الاستعادة والتراجع في الأقسام المختلفة.
5. تفاصيل واجهة التحذير قبل الاستعادة والتراجع.
6. حدود تسجيل الأحداث في المستودع الثانوي.
7. خيارات التخزين والنسخ الاحتياطي والتصدير.

**تنبيه:** هذه الخارطة مقترح لإدارة المشروع. تبقى الأفكار والمهام غير معتمدة حتى يراجعها المستخدم ويوافق عليها، ولا يوجد إصدار أو موعد إطلاق محدد.
